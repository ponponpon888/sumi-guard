# SUMI Guard：実行前記録と独立照合の設計

## 現在地

2026-10-03 の McAfee 検知について、Codex の SQLite を WAL 込みで読み直すと、
WAL を無視した読み方より追加データは得られました。しかし、2026-10-03
10:19〜10:22 JST の実行記録は見つかりませんでした。

これは「対象時刻の記録が、今回 WAL を含めて読めた取得物の範囲には無かった」という負の観測です。
PowerShell が実行されなかったこと、Codex が起動元でなかったこと、感染または誤検知の
いずれかを証明するものではありません。今回の原因調査はここで区切り、同種の事象を次回
追跡できるようにする設計へ移します。

この文書は設計だけです。フック、監査設定、サービス、Sysmon、ソフトウェアの導入や
既存設定の変更は行っていません。

## 配置先は暫定

ユーザーは SUMI Guard の統合先をまだ指定していません。前回この文書を
`ai-workforce/docs/` に置いたのは、調査時に見つかった既存リポジトリのうち、実行前フック、
Windows PowerShell、ガードレール、証跡の確度を既に扱っており、設計上の比較対象として
最も近かったためです。SUMI Guard を ai-workforce の一機能として確定した判断ではありません。

| 案 | 利点 | 分離すべき点 |
|---|---|---|

| 独立した Windows ツール／別リポジトリ | Codex以外の起動元、OSイベント収集、保存領域、権限、保持期間を独立して設計できる | フック共通部、状態定義、試験基盤が ai-workforce と重複し得る |

当面は、調査結果と設計判断を失わないための**文書だけを ai-workforce に仮置き**します。

Windows横断の収集が中心なら独立ツール、AIクライアント別フックの配布が中心なら

ROADMAP の参照にも「暫定配置」と明記します。

## 目的と不変条件

SUMI Guard は、取得できる実行経路について、実行前に少なくとも次を永続化します。

- SUMI Guard が発行する `execution_id`
- 呼び出し元が持つ `source_execution_id`（Codex では `tool_use_id`）
- 実行直前に渡される本文の SHA-256
- 本文の取得状態、バイト長、エンコーディング、ハッシュ対象の定義
- 呼び出し元、セッション、ターン、ツール、時刻、作業ディレクトリ

実行前フックの成功は「意図レコードを保存し、呼び出し元へ制御を返した」という意味だけです。
プロセス生成や本文の実行、正常終了を意味しません。

初版は `MONITOR`（監視モード）です。アプリ側の実行前記録が永続化できなくても、それを理由に
自動denyせず、元の実行判断へ介入しません。代わりに、本文を含まない `COLLECTION_FAILED` の
通知を一次保存先とは別の通知経路へ送ります。記録失敗時に実行を拒否する
`ENFORCE_RECORDING`（強制モード）は将来の明示的な選択肢とし、初版と最小試作には含めません。

## 3 種類のイベント

実行状態を 1 行の上書きで表さず、次のイベントを別々に追記します。

| イベント | 発生点 | 主な内容 | そのイベントだけで言えること |
|---|---|---|---|
| `ExecutionIntentRecorded` | アプリの実行前接続点 | `execution_id`、元の呼び出しID、ツール、本文ハッシュ、本文取得状態 | 実行が要求され、実行前記録が保存された |
| `ProcessObserved` | アプリとは独立したOS収集器 | PID、親PID、プロセス開始時刻、イメージ、コマンドライン取得状態、OSソース | OS上でプロセス生成が観測された |
| `ExecutionOutcomeObserved` | アプリの終了通知またはOSの終了観測 | 成功・失敗・終了コード・タイムアウト・結果不明、結果ソース | そのソースが終了結果を観測した |

3イベントはそれぞれ固有の `event_id`、発生時刻、収集時刻、収集元を持ちます。
`ExecutionIntentRecorded` だけなら「実行済み」ではありません。`ProcessObserved` があっても、
対象本文が最後まで実行されたとは限りません。`ExecutionOutcomeObserved` も、アプリ報告とOS終了の
どちらかを `outcome_source` で区別し、一方を他方の証明に使いません。

イベントから導出する相関は、次の3値です。

| 値 | 意味 |
|---|---|
| `DIRECT_MATCH`（直接一致） | 実行器が返したPIDと開始時刻、または実行IDを伝達できる同一接続点によって直接結び付いた |
| `INFERRED_MATCH`（推定一致） | 親子PID、時刻、イメージ、作業ディレクトリ、取得可能なハッシュ等の複数条件から一意候補を推定した |
| `UNMATCHED`（未照合） | 一方にしか記録がない、候補が複数、または照合に必要な項目がない |

時刻だけの近さは `DIRECT_MATCH` にしません。推定条件、候補数、時刻差を保存し、推定を直接一致へ
昇格させません。照合結果は元イベントを変更せず、再評価可能な派生記録として保持します。

実行前イベントの最小形は次です。これはスキーマ案であり、実装済みの形式ではありません。

```json
{
  "schema_version": 1,
  "event_id": "generated-event-id",
  "event_type": "ExecutionIntentRecorded",
  "execution_id": "generated-by-sumi-guard",
  "occurred_at_utc": "RFC3339 timestamp",
  "observed_at_utc": "RFC3339 timestamp",
  "source": {
    "app": "codex",
    "session_id": "source-session-id",
    "turn_id": "source-turn-id",
    "source_execution_id": "source-tool-use-id",
    "tool_name": "Bash"
  },
  "body": {
    "content_status": "CAPTURED_REDACTED",
    "raw_input_sha256": "sha256:lowercase-hex",
    "redacted_body_sha256": "sha256:lowercase-hex",
    "byte_length": 0,
    "hash_scope": "codex-tool-input-command-json-string-to-utf8-v1",
    "redacted_content_ref": "separate-protected-record",
    "encrypted_original_ref": null
  }
}
```

`execution_id` は SUMI Guard 内の主キー、`source_execution_id` は呼び出し元との照合キーです。
同じ値だと仮定しません。再試行も別 `execution_id` とし、同じ本文ハッシュを重複排除の根拠に
使いません。

## 収集状態

状態は 1 個の総合ステータスへ潰さず、少なくとも次の軸を独立して持ちます。

| 軸 | 値 | 意味 |
|---|---|---|
| `coverage_status` | `IN_SCOPE` / `OUT_OF_SCOPE` | その経路が設計上の取得対象か |
| `collection_status` | `RECORDS_FOUND` / `NO_RECORD` / `COLLECTION_FAILED` | 対象ソースの収集結果 |
| `content_status` | `CAPTURED_REDACTED` / `CAPTURED_ENCRYPTED` / `HASH_ONLY` / `CONTENT_UNKNOWN` / `NOT_APPLICABLE` | 実行本文の取得結果 |
| `correlation_status` | `DIRECT_MATCH` / `INFERRED_MATCH` / `UNMATCHED` | アプリ記録と OS 記録の対応強度 |
| `execution_status` | `INTENT_ONLY` / `PROCESS_OBSERVED` / `SUCCEEDED` / `FAILED` / `RESULT_UNKNOWN` | 3イベントから導出した状態 |

特に、次の 3 つを同じ「不明」へまとめません。

- `NO_RECORD`: そのソースを対象時間全体について正常に読み、該当行が 0 件だった
- `COLLECTION_FAILED`: 読み取り、スナップショット、構文解析、期間網羅性のいずれかを証明できなかった
- `CONTENT_UNKNOWN`: 実行の存在は観測したが、実行本文を復元できない

例えば、OS が PowerShell 起動を記録し、アプリ履歴を正常に読めたものの該当行がない場合は、
アプリの `collection_status=NO_RECORD`、本文の `content_status=CONTENT_UNKNOWN` とします。
アプリ DB のコピーが不整合なら `COLLECTION_FAILED` であり、`NO_RECORD` にはしません。

### 収集失敗の別通知経路

一次イベント保存が失敗した場合、監視モードのフックはdenyを返さず、最小の失敗通知だけを
別アダプターへ渡します。通知に実行本文、トークン、認証情報は含めません。

```json
{
  "event_type": "CollectionFailureNotice",
  "execution_id": "generated-by-sumi-guard",
  "occurred_at_utc": "RFC3339 timestamp",
  "failed_stage": "intent-store",
  "collection_status": "COLLECTION_FAILED",
  "reason_code": "IO_ERROR",
  "content_included": false
}
```

最小試作では、一次イベントファイルとは別の試験用通知ファイルと、Codexが受理する場合の
`systemMessage` / 標準エラー通知を候補にし、実際に届いた経路だけを記録します。恒久実装では
通知先を交換可能にし、一次保存先と同じDBトランザクションには載せません。

ただし、別通知ファイルも書けない、Codexへ応答を返せない、フック自体が起動しない、または
通知表示が保存されない場合、アプリ側には `COLLECTION_FAILED` さえ残らない可能性があります。
OS側の独立観測が残れば「意図記録のないプロセス」として検出できますが、OS側も収集できなければ
完全な無記録となり、SUMI Guardだけで欠落の有無を証明できません。この限界を監視モードの
既知の非保証として表示します。

将来の `ENFORCE_RECORDING` は、ユーザーが明示的に有効化し、通知経路を含む障害試験を通した
場合だけ、一次保存失敗をdenyへ変更できる別モードとして設計します。監視モードの既定値を
暗黙に強制モードへ昇格させません。

## 本文、ハッシュ、秘密情報の保存

SHA-256 は同じ本文かを比較する識別子であり、ハッシュから本文を復元して静的分析することは
できません。外部通信、ダウンロード、難読化、永続化、認証情報アクセス等を後から分析するには、
取得できた本文そのものが必要です。そのため、メタデータ、伏せ字後本文、暗号化原本を分離します。

| 層 | 保存範囲 | アクセス | 鍵管理 | 保持期間・容量上限 |
|---|---|---|---|---|
| メタデータとハッシュ | 全 `IN_SCOPE` イベント。ID、時刻、取得状態、長さ、ハッシュ、相関根拠 | SUMI Guard実行主体と対象Windowsユーザー。通常レポートはこの層だけ | 秘密鍵なし。保存領域はNTFS ACLで他の一般ユーザーを除外 | 90日、合計100MiB。期限切れから削除し、満杯時は収集失敗を記録 |
| 伏せ字後本文 | 取得できた本文から既知のトークン、資格情報、秘密値を伏せたもの | 同上。通常診断で本文を自動表示しない | 1件ごとにAES-256-GCMと固有nonce。伏せ字本文専用のデータ鍵をWindows DPAPI CurrentUserで保護し、イベントDBと別に保存。鍵IDを記録し90日ごとにローテーション | 30日、1件1MiB、合計250MiB |
| 暗号化原本 | 初期状態では保存しない。事前に指定した取得元だけ明示的に有効化 | 対象ユーザーによる個別のフォレンジック取得だけ。UI、AI分析、通常ログから参照しない | 1件ごとにAES-256-GCMと固有nonce。原本専用のデータ鍵をWindows DPAPI CurrentUserで保護し、イベントDB・伏せ字本文用鍵と別に保存。鍵IDを記録し90日ごとにローテーション | 7日、1件1MiB、合計100MiB。期限切れ原本と不要になった旧鍵を削除 |

管理者や同一ユーザー権限のプロセスによる改変まで防げるとは主張しません。将来サービス化する
場合は、ユーザー用DPAPI鍵を流用せず、専用サービスID、専用ACL、サービス用鍵保護へ設計を
分岐します。

1MiBを超える本文は原本も伏せ字後本文も完全取得扱いにせず、全入力をストリームで計算できた場合の
ハッシュと実バイト長だけを残して `HASH_ONLY`、理由を `CAPACITY_LIMIT` とします。切り詰めた先頭部を
本文全体として扱いません。本文領域が満杯でもメタデータ用に10MiBを予約し、ハッシュと失敗理由を
残します。メタデータ自体を永続化できなければ、初版の監視モードではdenyせず、前節の別経路へ
`COLLECTION_FAILED` を通知します。

Codex の `raw_input_sha256` は、`PreToolUse` の `tool_input.command` をJSON文字列として復号した後、
BOMなしUTF-8へ1回だけ符号化したバイト列を対象にします。改行、空白、Unicodeは正規化しません。
これは**フック入力文字列のハッシュ**であり、PowerShell内部のUTF-16表現、生成後のプロセス
コマンドライン、後続標準入力のバイト列を同一だと主張するものではありません。
伏せ字後は別の `redacted_body_sha256` を計算し、伏せ字規則版も記録します。将来、構造化ツール入力を
対象にする場合は、フィールド順を含むcanonical JSON規約を別の `hash_scope` として定義します。

## Codex の実行前接続点

2026-10-03 時点のこの PC は `codex-cli 0.160.0` で、機能一覧では `hooks` が
`stable / true` です。`~/.codex/hooks.json` は存在せず、`~/.codex/config.toml` にも
hooks 登録は見つかりませんでした。ここから確認できるのは、現在のバイナリが hooks 機能を持ち、
機能フラグ上は有効であることまでです。`PreToolUse` がこのPCで実際に発火すること、入力が文書通りの
形で届くこと、失敗時に想定通り動くことは実証していません。SUMI Guard はまだ接続されていません。

Codex の公式仕様では、`PreToolUse` がシェル、unified exec (`exec_command`)、
`apply_patch`、MCP、その他多くのローカル関数ツールの実行前に呼ばれます。シェルと
`exec_command` は `Bash` として一致し、入力には `session_id`、`turn_id`、
`tool_use_id`、`tool_input.command` が含まれます。これは実行 ID と本文ハッシュを
実行前に記録する接続点として使用できます。

公式仕様: [Hooks](https://learn.chatgpt.com/docs/hooks)

### 標準入力を2種類に分ける

「PowerShellが標準入力を読んだ」という観測だけでは、どの段階で本文が渡されたかを決めません。

| 区分 | 内容 | 実行前フックでの取得見込み |
|---|---|---|
| A. 初期コマンドの内部転送 | `tool_input.command` として依頼された初期コマンドを、実行基盤が内部実装としてPowerShellの標準入力へ渡す | 元の `tool_input.command` を `PreToolUse` で取得できる可能性がある。実際のラッパーや文字コードとの対応は最小試作で照合する |
| B. 起動後の追加入力 | 既に起動している実行セッションへ `write_stdin` で後から送る入力 | `write_stdin` 自体では新しい `PreToolUse` が発生しないため、追加本文はフックだけでは取得できない |

今回のMcAfee検知がBの経路だったとは断定しません。短いPowerShellラッパーと標準入力利用は、
Aの内部転送でも説明できる可能性があり、現在の証拠だけではA、B、その他の内部経路を区別できません。
最小試作では無害な固定文字列について、フックが受け取った初期入力のハッシュ、OS上の起動観測、
実行結果の固定出力を照合し、Aで元コマンドを取得できるかを確認します。Bは別ケースとして扱い、
追加本文を取得できない場合は `OUT_OF_SCOPE / CONTENT_UNKNOWN` のままにします。

ただし、次の境界があります。

| 経路 | 実行前記録 | 本文 | 設計上の扱い |
|---|---|---|---|
| Codex のローカル shell / `exec_command` | `PreToolUse` で可能 | 初期 `tool_input.command`。Aの内部転送でも元入力を取得できる可能性がある | 動作実証までは `IN_SCOPE / UNVERIFIED` |
| Bの既存 unified-exec セッションへの `write_stdin` | 再度 `PreToolUse` は発火しない | 後続の追加本文はフックだけでは取得不能 | `OUT_OF_SCOPE` かつ、実行観測時は `CONTENT_UNKNOWN` |
| Codex のホスト型ツール（例: WebSearch） | ローカルツールフックの対象外 | 取得不能 | `OUT_OF_SCOPE` |
| 既定フック経路を使わない特殊ツール | 保証なし | 保証なし | capability 検査で確認できなければ `OUT_OF_SCOPE` |
| Codex 外から起動した PowerShell | Codex フックでは取得不能 | OS コマンドライン等で見える範囲だけ | Codex 監視は `OUT_OF_SCOPE`、OS 監視は別評価 |

短いPowerShellラッパーが標準入力を読み込んで評価する形では、Aなら初期 `tool_input.command`、
Bなら起動後の追加本文という違いがあります。Aの取得可能性を実証する前に、ラッパーのハッシュを
実スクリプト本文全体のハッシュと扱いません。Bの追加本文を別途観測できなければ、その内容は
取得不能です。

また、公式仕様はフックのエラー、タイムアウト、不正な応答がツール実行を必ず止めるとは
していません。初版の監視モードは、この挙動に追加の自動denyを重ねず、保存失敗を別通知へ
試みます。将来の強制モードで明示的なdenyを返せても、フック未起動まで含めた完全なfail-closed
境界にはなりません。SUMI GuardはOS側の独立監視で欠落の検出を試み、この制約をレポートに
残します。

### 最小試作で確認する Codex 側の項目

ユーザー設定ではなく専用の一時プロジェクトを使い、次の4点を確認します。具体的な順序は
[最小試作の作業計画](#最小試作の作業計画)にまとめます。今回はフック登録も試験実行も行いません。

- 無害な固定入力で、トップレベル項目名、型、`tool_name`、`tool_use_id`、
  `tool_input.command` のハッシュを保存し、実際の入力スキーマを固定する
- `ExecutionIntentRecorded` が固定コマンドの結果より先に保存されることを確認し、フック成功を
  実行成功として扱わない
- 一次保存失敗、フック非ゼロ終了、タイムアウト、不正JSONについて、継続・警告・拒否の実挙動を
  記録する。SUMI Guardの監視モード自身は保存失敗を理由とするdenyを返さない
- Aの初期入力ハッシュと固定出力を照合し、Bの後続入力は別ケースとして取得可否を報告する

この実証が成功するまでは、Codex対応を「設計済み・接続未検証」と表示します。

## アプリ記録と OS 記録を分離する

同じ収集器から見かけ上2種類の記録を作らず、障害領域と保存先を分けます。

```text
Codex PreToolUse ──> ExecutionIntentRecorded ─┐
                                              ├─> correlation assessment
Windows process source ──> ProcessObserved ──┤
                                              │
app/OS completion source ─> ExecutionOutcomeObserved
```

アプリ側は `execution_id`、`source_execution_id`、本文ハッシュ、本文取得状態、セッション情報を
持ちます。実行前イベントは子PIDを持たないことを正常とします。実行器が子PIDを返せる接続点を
将来使う場合も、PIDと開始時刻を別の起動通知または相関根拠へ記録し、過去の意図イベントを
「実行済み」へ上書きしません。

OS側は、利用可能な既存ソースからPID、親PID、生成時刻、イメージ、コマンドライン取得状態、
終了状態を収集します。候補は既存のSecurity 4688、Sysmon Event 1、PowerShell Operational、
または設定変更を要しないリアルタイムのWindowsプロセス通知です。最初の実証で利用可能性を比較し、
アプリとは独立して取得できる1経路だけを選びます。ソースが無効、未導入、または読めなくても、
成功を作るために監査設定変更や導入を行いません。

相関は前節の `DIRECT_MATCH`、`INFERRED_MATCH`、`UNMATCHED` の3値だけを使います。
過去PIDを現在のプロセス一覧で補完せず、PIDの再利用を避けるため開始時刻と組み合わせます。
アプリ記録とOS記録のどちらかが欠けても、もう一方を削除、補完、成功扱いにしません。

## SQLite と WAL の整合取得

SQLite の履歴読み取りは補助経路です。SUMI Guard 自身の実行前記録は、後からアプリ DB を
推測して読む方式だけに依存させません。

取得方式の優先順位は次です。

1. アプリ所有プロセスが提供する、同一読み取りトランザクションからのエクスポート
2. SQLite Online Backup API を使い、`immutable=1` を付けずに WAL を見える接続から
   新規スナップショット DB へバックアップ
3. VSS 等、DB・WAL・SHM を同一時点として取得できるファイルシステムスナップショット
4. DB・WAL・SHM の通常ファイルコピーは調査用の best effort に限定

原本へ checkpoint を実行しません。原本の journal mode や設定も変更しません。
`immutable=1` は未 checkpoint の WAL を無視し得るため、WAL を含む取得には使用しません。

スナップショットには取得方式、開始・終了時刻、SQLite の戻り値、対象パス、各コピーの
SHA-256、スキーマ版、照会期間を記録します。取得後はコピーに対して `PRAGMA integrity_check`
を実行し、必要なテーブルと期間が照会できることを確認します。Online Backup API の完了または
同一時点スナップショットの成立と、取得後検査の両方が揃って初めて、収集成功とします。

コピー前後のファイルサイズと更新日時が一致しても、その間に同サイズの書き換え、WAL の
ローテーション、世代不一致が起きていない証明にはなりません。サイズ・更新日時は診断情報として
残しますが、整合性保証には使いません。DB・WAL・SHM の通常コピーが読めた場合も、その事実だけで
`NO_RECORD` を確定せず、取得方式の保証が不足すれば `COLLECTION_FAILED` または
best-effort の未確定結果にします。

## 無害な検証設計

本番設定や保護機能を止めず、専用の試験保存先とテストダブルで次を検証します。
これは実装後の試験計画であり、今回は実行していません。

| ケース | 無害な入力・故障注入 | 期待する記録 |
|---|---|---|
| 通常実行 | `Write-Output 'SUMI_GUARD_TEST_OK'` | 意図・OS起動・終了結果が別イベント。直接または推定の根拠を伴って照合 |
| 実行失敗 | `exit 23` | 意図・OS起動・失敗結果を別イベントで残す。意図だけを実行失敗とみなさない |
| 収集停止 | 実サービスを止めず、隔離した収集器テストダブルを停止または書き込み失敗にする | 自動denyせず、別経路へ `COLLECTION_FAILED` を試みる。空の成功結果や `NO_RECORD` にしない |
| アプリ履歴欠落 | OS 側の無害なプロセス記録だけをフィクスチャに残し、アプリ履歴を意図的に省く | アプリは `NO_RECORD`、OS は `RECORDS_FOUND`、本文は `CONTENT_UNKNOWN`、照合は `UNMATCHED` |
| WAL 未反映 | fixture DB の未 checkpoint WAL に対象行を置く | WAL 対応スナップショットでは検出し、`immutable=1` の結果を合格根拠にしない |
| 標準入力追加 | 長時間待機する隔離テストプロセスへ無害な文字列を `write_stdin` 相当で送る | 初期コマンドと後続本文を区別。stdin 取得機構がなければ `OUT_OF_SCOPE / CONTENT_UNKNOWN` |

各試験は本文そのものを通常出力せず、期待したハッシュ、状態、件数、照合強度だけを比較します。
「テストプロセス終了コード 0」だけで成功にせず、レコードの存在、順序、ID、ハッシュ、
状態遷移を検査します。収集器停止とアプリ履歴欠落は異なる期待値にし、両方を同じ空配列で
合格させません。

## 最小試作の作業計画

最初の試作は、**Windows上で無害な固定1コマンドについて、実行前イベントを保存し、独立した
OS側の起動観測と照合して、取得できた範囲と限界を報告すること**だけに限定します。
利用者の実コマンド、既存履歴、認証情報、業務データは収集しません。

1. `%TEMP%` 配下に固有名の専用一時プロジェクト、試験用イベント保存先、別通知先を作る。
   ユーザーの `~/.codex`、ai-workforceの設定、既存ログ保存先は使わない。
2. 一時プロジェクトだけに試験用 `PreToolUse` を接続し、固定コマンド
   `Write-Output 'SUMI_GUARD_PROTOTYPE_OK'` の `ExecutionIntentRecorded` を保存する。
   保存する本文はこの固定文字列だけとし、実データは入力しない。
3. 既存監査設定を変更せず利用でき、Codexのイベント保存とは独立したOSプロセスソースを1つ選び、
   該当する `ProcessObserved` を取得する。読めるソースがなければ試作未達として報告する。
4. フック入力の固定文字列・ハッシュ、OSのPID・親PID・開始時刻・イメージ、固定出力または終了結果を
   照合する。Aの内部標準入力転送で元コマンドを取得できたかを確認し、直接一致、推定一致、未照合を
   根拠付きで判定する。Bの `write_stdin` は別ケースとして取得限界を確認する。
5. 一次保存失敗を模擬できる範囲では、監視モードが自動denyせず、本文なしの
   `COLLECTION_FAILED` を別通知先へ試みることを確認する。別通知も失敗した場合に証跡が残らない
   限界を報告する。
6. イベント3種のうち実際に得られたもの、得られなかったもの、相関強度、A/Bの判定可否、
   収集失敗時の通知可否を短い試作レポートへまとめる。
7. 一時プロジェクトと試験用ファイルだけを片付ける。恒久的なフック登録、サービス登録、
   インストール、監査設定変更、保護設定変更は行わない。

最小試作に、暗号化本文保存、鍵ローテーション、保持期間処理、容量制御、SQLite/WAL取り込み、
UI、AI分析、自動遮断、常駐サービスは実装しません。これらは試作結果と配置先の決定後に扱います。

## 段階別の受け入れ条件

### 設計完了

- ai-workforce配下が暫定配置であり、独立Windowsツール案との判断基準が記載されている
- `MONITOR` と将来の `ENFORCE_RECORDING` が分離され、初版は保存失敗で自動denyしない
- 一次保存、別通知、OS観測の全てが失敗した場合は無記録になり得ると明記されている
- 意図、OS起動、終了結果が別イベントで、フック成功だけを実行済みと表示しない
- `DIRECT_MATCH`、`INFERRED_MATCH`、`UNMATCHED` と、`NO_RECORD`、
  `COLLECTION_FAILED`、`CONTENT_UNKNOWN` が区別されている
- 標準入力AとBが分離され、今回の検知がBだったとは断定していない
- 機能フラグ確認と実動作実証が別項目で表示されている
- ハッシュだけでは本文を分析できないことと、後続段階の本文保護方針が定義されている

### 最小試作完了

- 専用一時プロジェクト以外へ恒久的な設定変更をしていない
- 無害な固定文字列以外の実データを収集していない
- `PreToolUse` の実入力スキーマと実行前発火を実測し、`ExecutionIntentRecorded` を保存できた
- アプリ側と独立したOSソースから、同じ試験の `ProcessObserved` を取得できた
- 両イベントを `DIRECT_MATCH`、`INFERRED_MATCH`、`UNMATCHED` のいずれかで根拠付き評価した
- Aの初期入力と固定実行結果を照合し、Bの後続入力について取得可否を別に報告した
- 監視モードの保存失敗が自動denyにならず、別通知の成否と無通知になり得る限界を報告した
- 一時フック、試験用イベント、OS観測の取得限界をまとめた試作レポートがある

暗号化、鍵管理、保持期間、容量制御、WAL取り込み、UI、AI分析、自動遮断は、最小試作完了の
前提にしません。

### 運用開始

- 試作結果をもとに、ai-workforce内か独立Windowsツールかをユーザーが決定している
- 対象アプリ、対象経路、OSソース、必要権限、運用責任者、復旧手順が確定している
- 伏せ字後本文または暗号化原本を扱う場合、ACL、鍵管理、保持期間、容量上限が実装・試験されている
- 必要な場合だけ、WALを含む整合取得が実装・試験され、原本へcheckpointしないことを確認している
- 収集停止、アプリ履歴欠落、OS記録欠落、容量超過、別通知失敗を区別して検出できる
- 通常ログ、通知、診断レポートへ秘密情報を出さないことを確認している
- `ENFORCE_RECORDING` を提供する場合、監視モードとは別の明示設定、解除手順、障害試験がある

運用開始条件を満たすまでは、SUMI Guardを完全な監査証跡または感染判定器とは呼びません。
